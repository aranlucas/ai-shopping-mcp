`fae55db`. The run was non-interactive, so nobody picked which findings to
plan. **The default selection was used**: the top findings by leverage became
plans, and the rest are listed below without plans.

## Direction suggestions

- **Delete saved shopping lists (plan 001, shipped).** Lists can be created,
  read and edited but never removed: `ShoppingListStore` has no delete, and
  every `create_shopping_list` and `prepare_meal_plan` adds a row forever. Weekly
  use makes the no-argument index longer and name lookups ambiguous.
  `IMPROVEMENTS.md` names "no tool deletes … shopper data" as an open risk. The
  trade-off is a new destructive tool; it is shopper-scoped, annotated
  `destructiveHint`, and the app asks for confirmation.
- **Weekly templates ("reuse last week's list").** This is a `ROADMAP.md`
  post-pilot priority. The pieces exist: `get_shopping_list` and the
  pantry/deal item flags in `create_shopping_list`. A `copy_shopping_list` with
  a pantry-review summary is a medium-sized spike. Wait for the pilot signal, as
  the roadmap says.
- **Per-shopper rate limit.** This is an open risk in `IMPROVEMENTS.md`.
  Cloudflare's rate-limiting binding keyed by `(issuer, subject)` in
  `composition.ts` would cover it, but it adds a binding to
  `cloudflare.config.ts`, and CI can't fully verify that without a deploy.

## Why plan 001 was the one shipped

The brief asked for the highest-leverage plan that is either a grounded
user-facing feature or a substantial correctness or security fix that the repo's
tests can verify. Plan 001 is the only user-facing feature in the set. It fills
the one missing verb in the shopping-list CRUD surface, which shoppers hit every
week. It reuses established contracts: shopper-scoped D1 queries, `safeStorage`
and `toMcpError`, and the existing `shopping_lists` app view. Worker D1 tests,
tool tests, view-helper tests and the MCP contract test verify it fully. Plan
002 has a better impact-to-effort ratio and should go next. It is a few lines
on a failure-only path, so it is a small fix rather than the substantial one
the brief prioritized.

## Findings considered and rejected

- Tenant isolation / IDOR on `listId`, `planId`, `orderId`: every D1 query is scoped by `userId`. No leak found.
- Cart retries, pending-entry expiry, fractional cart packages, duplicate exact list names, pantry decrement races: already fixed or documented as by-design (`docs/reliability-audit.md`).
- Multi-step `update_shopping_list` is not atomic: documented by design; earlier committed edits are reported.
- Cross-client cart deduplication: documented limitation, not a bug.
- Dependency posture: `pnpm audit --prod` is clean; no major-version migration is pressing.
- `pantry.updateQuantity` has no callers: real dead code, but too small to plan.
