## Exact exchange contract

Send a URL-encoded POST to `https://auth.aranlucas.workers.dev/api/auth/oauth2/token`, authenticated as an explicitly provisioned confidential client; Auth documents HTTP Basic client credentials. The client must be registered for the exchange grant and linked to the relevant resources. The beta's resource-aware `adminCreateOAuthClient()` API is server-only; do not assume posting resource fields to ordinary HTTP client creation provisions them. [Auth exchange guide](https://github.com/sidequest-labs/auth/blob/4d4bae4297c1a042577380d21e74b10949428820/docs/oauth.md#token-exchange-between-auth-resources), [provisioning caveat](https://github.com/sidequest-labs/auth/blob/4d4bae4297c1a042577380d21e74b10949428820/docs/linked-provider-tokens.md#provisioning-one-administrator-action-per-cli-client).

```text
grant_type=urn:ietf:params:oauth:grant-type:token-exchange
subject_token=<Auth-issued user access token>
subject_token_type=urn:ietf:params:oauth:token-type:access_token
resource=<registered target resource identifier>
scope=<permitted subset of subject scopes>
```

The implementation also accepts registered target identifiers in `audience`, including repeated targets. The exchanging client must be the subject token's client or a resource server linked to its audience. Scopes cannot exceed the subject/client/resource policies; `openid` and `offline_access` cannot be exchanged. User consent must cover the exchanging client, effective scopes and targets unless it was deliberately provisioned with `skip_consent`. Actor-token delegation is rejected. [Versioned native implementation](https://github.com/better-auth/better-auth/blob/v1.8.0-beta.2/packages/oauth-provider/src/token-exchange.ts).

The result is an **Auth-issued access token**, with the same user `sub`, the exchanging client's `client_id`, target `aud`, retained `reference_id`/`sid` where present, and expiry no later than the subject's expiry. It returns `issued_token_type=urn:ietf:params:oauth:token-type:access_token`, without refresh or ID tokens. Auth's test verifies `typ: at+jwt`, JWKS validation, scope/target/consent rejection, and rejection of session-bound subjects after sign-out. It does not test an exchange with `mcp:tools`: its successful example narrows a shopping-audience token to Auth's resource with `email`. [Native implementation](https://github.com/better-auth/better-auth/blob/v1.8.0-beta.2/packages/oauth-provider/src/token-exchange.ts), [Auth regression test](https://github.com/sidequest-labs/auth/blob/4d4bae4297c1a042577380d21e74b10949428820/test/token-exchange.test.ts).

## Compatibility and consumer action

Keep these settings and behavior:

- Issuer: `https://auth.aranlucas.workers.dev/api/auth`.
- JWKS: `https://auth.aranlucas.workers.dev/api/auth/jwks`.
- Shopping resource/audience: `https://ai-meal-planner-mcp.aranlucas.workers.dev/mcp`, with `mcp:tools`; access-token lifetime remains 15 minutes.
- `AUTH` service binding to Worker `auth`, named export `KrogerTokens`; `accessToken(userId)` returns `{accessToken: string, expiresAt: number}` (epoch milliseconds) or `null`. The verified JWT `sub` remains the Auth user ID. Auth still serializes provider refreshes in its per-user broker.

These contracts match shopping's configuration, verifier and RPC interface. #71 does not change Auth's Kroger entrypoint, broker client, Kroger implementation or resource constants. Auth's root resource `https://auth.aranlucas.workers.dev` is a separate audience; its root protected-resource metadata must not replace shopping's own metadata or `/mcp` audience. Existing shopping client resource links and consents are retained. [Auth resources and policy](https://github.com/sidequest-labs/auth/blob/4d4bae4297c1a042577380d21e74b10949428820/src/auth.ts), [resource constants](https://github.com/sidequest-labs/auth/blob/4d4bae4297c1a042577380d21e74b10949428820/src/config.ts), [Kroger token contract](https://github.com/sidequest-labs/auth/blob/4d4bae4297c1a042577380d21e74b10949428820/src/kroger.ts), [shopping config](../cloudflare.config.ts), [shopping verification](../src/services/better-auth.ts), [shopping RPC](../src/services/auth-rpc.ts), [registration migration behavior](https://github.com/sidequest-labs/auth/blob/4d4bae4297c1a042577380d21e74b10949428820/docs/oauth.md#mcp-clients).

Recommendations:

1. **Retain direct MCP JWT verification and the private Kroger RPC.** No exchange client, secret, shopping migration or dependency upgrade is required merely to consume Auth's JWTs. The consumer's `1.7.12` verifier accepts the documented token format; full cross-version runtime validation remains to be performed. Auth's `0014` migration belongs to the upstream beta deployment. [Shopping verifier](../src/services/better-auth.ts), [Auth migration guidance](https://github.com/sidequest-labs/auth/blob/4d4bae4297c1a042577380d21e74b10949428820/docs/oauth.md#database-and-deployment).
2. The [integration documentation](better-auth-integration.md) now records consumer `1.7.12`, provider `1.8.0-beta.2`, token exchange, and Auth's refresh serialization. Shopping's duplicate `KrogerConnections` coordinator is removed in favor of direct RPC, retaining response validation and unlink/outage handling. A signed-fixture regression case verifies that the exchanging client's ID and retained session/reference claims preserve shopping identity through the real MCP transport. `pnpm lint`, `pnpm typecheck`, `pnpm build:worker`, and all 803 tests passed. Production login, shopping, refresh, Kroger unlink/recovery, and a successful exchange remain untested in this investigation.
3. Add exchange only if shopping later calls a **different Auth-protected downstream resource**. That requires an explicitly provisioned confidential client, resource links, consent and suitable incoming scopes. Auth-root `email` tokens cannot acquire `mcp:tools`; the current Auth-root resource policy excludes that scope. The shopping verifier should continue rejecting tokens without its exact audience and scope. [Auth exchange policy](https://github.com/sidequest-labs/auth/blob/4d4bae4297c1a042577380d21e74b10949428820/src/auth.ts), [native scope checks](https://github.com/better-auth/better-auth/blob/v1.8.0-beta.2/packages/oauth-provider/src/token-exchange.ts).
4. Do not adopt #72's public linked-account APIs for Kroger. That separate resource exports consented **Google/ChatGPT** access tokens only; Kroger is explicitly excluded and remains available through private RPC. [Linked-provider contract](https://github.com/sidequest-labs/auth/blob/4d4bae4297c1a042577380d21e74b10949428820/docs/linked-provider-tokens.md#server-coordination-and-deployment).
